BCS70 variable atlas · the whole loop

The Atlas Loop

Twenty-eight ways to compute BMI, and two thirds of them never written down. The atlas is an attempt to make a derived variable something you find rather than something you rebuild. This is how it works, end to end.

Why this exists

Everyone builds it again

We scraped the published literature that uses BCS70 and pulled the methods apart — 391 papers found, 237 with a workflow we could extract, 5,890 variables recorded as raw or derived. Then we asked a narrow question of it: when two papers use the same construct, do they build it the same way?

28 distinct ways BMI was derived, across 65 papers one construct
66% of variables were named but never had their derivation stated 3,882 of 5,890 rows
4,026 distinct recipes for 3,352 constructs — 335 of them contested the ledger of what exists
0.88 design recurrence — at 1.00 every paper is its own pattern near-total non-reuse

Twenty-five years of researchers have each rebuilt body mass index from height and weight, twenty-eight different times, and two thirds of them never wrote down how.

None of that is anyone's fault — there was nowhere to put a derivation so that the next person could find it. It is expensive in three separate ways: the work is redone, the results are not comparable, and most of it cannot be reproduced at all, because the recipe was never recorded. Childhood socioeconomic position was built sixteen ways across forty-seven papers. Educational attainment, twelve ways across thirty-three.

One source of truth

A construct is derived once, in the open, from named source variables. The next paper cites the variable rather than re-inventing it — and two papers using it are using the same thing.

Reproducible and traceable

Every variable in the ledger carries the script that produced it, the sweeps it draws on, the raw items it reads, and the record of it having been run against the real files. The recipe cannot go unstated, because the recipe is the artefact.

Nobody starts from nothing

Where a variable exists you download working R. Where it does not, an agent writes a first cut against the real dictionary and an interview turns a rough idea into a request precise enough to build.

Figures from method-miner, a scrape of the BCS70 literature via OpenAlex and Europe PMC, run 27 August 2026. Constructs and recipes are the ledger's collapsed counts — one entry per construct and derivation method, not one per paper.

Four things worth knowing

One runtime, three agents

What differs between them is a prompt and a lifecycle — when the turn ends, whether the checklist moves, whether the extractor runs. The streaming, the hop budget and the four lookups are shared. A graph each would have duplicated all of it to change a system prompt.

Getting in takes a yes

The interview is withheld from the router entirely; the only way in is a proposal the researcher accepts. A wrong route costs a turn — being put into an interview unasked costs more, and the confirmation is what pays the difference.

Only the small model crosses the wall

The frontier model writes the code and judges the contract; it never sees a row. The model that does see rows is small, local, and stays inside. What passes between them is code one way and a filled-in data contract the other — never data.

The ledger is both ends of the loop

It is what list_harmonised searches when the assistant asks whether something already exists, what a merge adds to, and what a researcher downloads. The same store closes the circle.
